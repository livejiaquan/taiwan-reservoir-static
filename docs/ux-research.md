# 使用者研究

這份文件用軟體工程的需求分析角度，整理誰會打開這個頁面、在什麼情境下打開、要完成什麼事，以及頁面必須守住的非功能需求。它是改版時做取捨的依據：任何設計選擇都要能回答「這幫哪個 persona 完成哪件事」。

> 研究方法：沒有做訪談或問卷。persona 由三個來源推論：(1) 水利署開放資料欄位能回答什麼問題；(2) 枯水期新聞與社群討論中常見的提問（「水庫還剩多少」「會不會限水」）；(3) 同類產品（見 [design-research.md](design-research.md)）把哪些資訊放在第一屏。結論應視為假設，上線後可用 GitHub Pages 流量來源與裝置比例校正。

## Persona

### 1. 關心限水的上班族｜陳小姐，34 歲，桃園

- **情境**：通勤時在捷運上看到「石門水庫蓄水率跌破五成」的新聞，想自己確認。
- **裝置**：手機，單手，網路可能不穩。
- **想知道**：我住的地方靠哪座水庫？現在幾 %？比昨天多還是少？要不要開始儲水？
- **痛點**：官方防災資訊網是表格，字小、欄位多，看不出「好或不好」。
- **成功標準**：5 秒內找到石門水庫、看懂它的狀態，並知道這個數字是幾點的資料。

### 2. 跑新聞的記者／內容創作者｜林先生，28 歲

- **情境**：枯水期要寫一則「全台水情」快訊，需要可以引用的數字與時間。
- **裝置**：桌面瀏覽器，同時開著水利署官網對照。
- **想知道**：全台總蓄水率、哪幾座低於警戒、各區差異、資料時間與來源。
- **痛點**：第三方網站常不標資料時間，或把過期資料當作即時。
- **成功標準**：一屏內拿到總覽數字、最低的幾座、資料來源與觀測時間，能直接截圖使用。

### 3. 農業與產業用水相關從業者｜王先生，52 歲，台南

- **情境**：一期稻作前關心曾文、烏山頭、南化的蓄水，判斷灌溉是否可能停灌。
- **裝置**：手機為主，字要大。
- **想知道**：南部水庫的蓄水與趨勢、水位離滿水位還有多遠。
- **痛點**：小字、要放大才看得到；英文或專業縮寫看不懂。
- **成功標準**：用「南部」篩選後，一眼比較三座水庫；數字不需要放大就讀得到。

### 4. 學生與資料愛好者（含作品集訪客）｜研究生，24 歲

- **情境**：做報告或看到這個 GitHub 作品集，想了解資料怎麼來、可不可信。
- **裝置**：桌面。
- **想知道**：資料來源、計算方式（蓄水率＝有效蓄水量÷有效容量）、失敗時怎麼處理。
- **成功標準**：頁面上就能找到資料說明，README 有截圖與線上連結。

## 前三項任務（依頻率與重要性排序）

| # | 任務 | 主要 persona | 頁面必須提供 |
|---|------|------------|------------|
| 1 | **確認「現在整體缺不缺水」** | 全部 | 第一屏的一句話結論：總蓄水率＋需留意的水庫數，加上資料時間 |
| 2 | **找到特定水庫的狀態與趨勢** | 1、3 | 依北到南分區的清單、每座的蓄水率、24 小時變化、觀測時間；可依地區篩選 |
| 3 | **判斷資料可不可信、多新** | 2、4 | 每座水庫的觀測時間與過期提示；資料無法驗證時明確說明，不顯示推測值 |

延伸任務（不放第一屏）：查看水位與滿水位差距、昨日集水區降雨、整體依蓄水率排序。

## 使用情境的設計推論

- **「一眼看懂」比「資料完整」重要**。官方網站已經有完整表格，這個頁面的價值是把 20 座水庫壓縮成一張圖、一句話。
- **好壞要用語意而不是數字表達**：沿用專案既有的四段門檻（≥80% 充足、50–80% 正常、30–50% 偏低、<30% 嚴重），顏色只標出需要留意的水庫，並且永遠搭配文字標籤，不只靠顏色。
- **時間是資料的一部分**：各水庫的觀測時間並不一致（有的每小時更新、有的一天一次），所以時間要跟著每一列走，而不是只放在頁首。
- **失敗要說清楚**：既有的「無法驗證就不顯示」原則是這個專案的可信度核心，改版必須保留，並且讓錯誤狀態提供下一步（重試、前往官方頁面）。

## 非功能需求

| 類別 | 需求 | 驗收方式 |
|------|------|--------|
| 正確性 | 保留既有信任檢查：涵蓋率不足、觀測時間無效或超過 48 小時就整體拒絕顯示；快取也要重新驗證 | `node --test` 既有測試全數通過 |
| 時效 | 每座水庫顯示觀測時間；超過 12 小時標示「較舊」（多數水庫逐時回報，部分一天回報一次，12 小時能區分「今天報過」與「真的落後」）；頁首顯示最新觀測時間與「幾分鐘前取得」 | 截圖與手動檢查 |
| 效能 | 首次載入不阻塞渲染；移除 Chart.js 與圖示字型等大型相依；Lighthouse Performance ≥ 90 | Lighthouse（行動裝置設定） |
| 無障礙 | WCAG 2.1 AA 對比；觸控目標 ≥ 44px；鍵盤可操作、焦點可見；狀態不只靠顏色；尊重 `prefers-reduced-motion` | Lighthouse Accessibility ≥ 90、手動檢查 |
| 響應式 | 390px 手機與 1440px 桌面都要好看；不能有水平捲動與版面跳動（CLS < 0.1） | 截圖、Lighthouse CLS |
| 主題 | 跟隨系統深淺色，也可手動切換並記住選擇 | 截圖 |
| 部署 | 維持純靜態、無建置步驟，GitHub Pages 直接從 `main` 根目錄發布 | 線上網址 |
| 隱私 | 不收集個資；只用 localStorage 存 5 分鐘快取與主題偏好 | 程式碼審查 |

## 裝置評估

結論：**手機是主力裝置，桌面同樣要好看**。

- 任務 1、2 多半發生在看到新聞之後的零碎時間，推估手機占 **65–75%**。台灣行動上網普及，新聞與社群分享連結也多在手機上被點開。
- 記者與作品集訪客（persona 2、4）主要用桌面，推估 **25–35%**；而作品集訪客正是這個 repo 想打動的人，所以桌面不能只是「可用」。
- 因此以 390px 為設計基準（mobile-first），再擴充到 1440px 的雙欄版面：桌面利用寬度把「水位刻度牆」完整攤開，並讓總覽側欄在捲動時保持可見。

這些比例是推論，沒有實際流量數據；上線後可從 GitHub Pages 的 traffic（需 repo 權限）或之後加上的隱私友善分析工具校正。
