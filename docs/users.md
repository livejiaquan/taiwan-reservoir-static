# 使用者與需求

這個頁面要回答一個問題：「現在水庫夠不夠用？」下面是我設計時假設的使用者與取捨。沒有做訪談或問卷；這些情境來自水利署資料能回答的問題，以及枯水期新聞與社群常見的提問（「水庫還剩多少」「會不會限水」），應視為假設，不是研究結論。

## 誰會用

| 誰 | 情境 | 主要裝置 | 想知道 |
|----|------|---------|-------|
| 關心限水的上班族 | 通勤時看到「石門水庫蓄水率跌破五成」的新聞，想自己確認 | 手機，單手 | 我家附近的水庫現在幾 %？比昨天多還是少？這個數字是幾點的？ |
| 記者、內容創作者 | 枯水期要寫一則全台水情快訊，需要可引用的數字與時間 | 桌面 | 全台總蓄水率、哪幾座偏低、各區差異、資料時間與來源 |
| 農業與產業用水相關人員 | 一期稻作前關心曾文、烏山頭、南化的蓄水 | 手機，字要大 | 南部水庫的蓄水與趨勢、離滿水位還有多遠 |
| 學生與資料愛好者 | 做報告時想知道資料怎麼來、可不可信 | 桌面 | 資料來源、計算方式、失敗時怎麼處理 |

## 前三項任務

1. **確認整體缺不缺水**：第一屏給出總蓄水率與一句結論，並標明資料時間。
2. **找到特定水庫的狀態與趨勢**：依北、中、南分區列出，每座有蓄水率、24 小時變化與觀測時間，可依地區篩選。
3. **判斷資料可不可信、多新**：每座水庫標示自己的觀測時間，超過 12 小時標示「較舊」；資料無法驗證時說明原因，不顯示推測值。

## 設計取捨

- **一眼看懂比資料完整重要**。水利署官方頁面已有完整表格；這個頁面把 20 座水庫壓縮成一張圖和一句話。
- **顏色只標需要留意的水庫**。門檻是 ≥80% 充足、50–80% 正常、30–50% 偏低、<30% 嚴重；只有偏低與嚴重會用琥珀與紅色，而且一律附文字標籤，不單靠顏色。
- **時間跟著每一列走**。各水庫的回報頻率不同（多數每小時，少數一天一次），只在頁首放一個時間會誤導。
- **無法驗證就不顯示**。這是專案的可信度核心：API 失敗、涵蓋不足半數水庫、觀測時間無效或超過 48 小時，整頁不顯示數字，並提供重試與水利署官方頁面的連結。

## 非功能需求

| 類別 | 需求 |
|------|------|
| 正確性 | 保留信任檢查，快取讀出時也重新驗證；`node --test tests/` 全數通過 |
| 效能 | 純靜態、無框架、無建置；首次繪製不被第三方資源阻塞；Lighthouse 效能 ≥ 90 |
| 無障礙 | 對比符合 WCAG 2.1 AA；觸控目標 ≥ 44px；鍵盤可操作、焦點可見；狀態不只靠顏色；尊重 `prefers-reduced-motion` |
| 響應式 | 390px 手機與 1440px 桌面都能用；不水平捲動；版面不跳動（CLS < 0.1） |
| 主題 | 預設淺色，可切換深色並記住選擇 |
| 隱私 | 不收集個資；只用 localStorage 存 5 分鐘資料快取與主題偏好 |

## 裝置

我假設手機是主力（約七成）：多數查詢發生在看到新聞後的零碎時間。桌面（約三成）以記者與資料愛好者為主，所以桌面版也用整面寬度把 20 座水庫攤開，而不是放大的手機版。沒有流量數據佐證，這些比例只是推測。
